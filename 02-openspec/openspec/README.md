# OpenSpec-подход в проекте

Спецификации идут перед кодом. Крупное изменение сначала описывается спецификацией, потом
реализуется по чек-листу задач, проверяется на соответствие спеке и архивируется.

## Структура

```
openspec/
├── README.md            — этот файл
├── specs/               — актуальные (действующие) требования
└── changes/
    ├── <слаг>/          — изменение в работе
    │   ├── proposal.md  — зачем и что меняется, границы
    │   ├── specs/       — требования и сценарии (дельты ADDED/MODIFIED/REMOVED)
    │   ├── design.md    — технический подход
    │   └── tasks.md     — чек-лист задач
    └── archive/
        └── <ГГГГ-ММ-ДД>-<слаг>/  — завершённые изменения
```

## Процесс

1. `/исследовать <тема>` — изучить проблему и код, без изменений.
2. `/предложить <название>` — создать папку изменения с артефактами.
3. `/реализовать <изменение>` — выполнить задачи из `tasks.md`.
4. `/проверить <изменение>` — сверить реализацию со спекой.
5. `/архивировать <изменение>` — перенести требования в `specs/`, папку — в `archive/`.

Конвенции формата требований и сценариев — в навыке «Работа со спецификациями».
