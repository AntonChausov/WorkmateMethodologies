# Работа со спецификациями (OpenSpec-подход)

Подход: сначала спецификация — потом код. Крупное изменение описывается как спецификация в папке
`openspec/`, реализуется по чек-листу задач, проверяется на соответствие спеке и архивируется.

## Структура папки `openspec/`

```
openspec/
├── README.md            — описание процесса
├── specs/               — актуальные (действующие) требования
└── changes/
    ├── <слаг>/          — изменение в работе
    │   ├── proposal.md  — зачем и что меняется, границы
    │   ├── specs/       — требования и сценарии (дельты)
    │   ├── design.md    — технический подход
    │   └── tasks.md     — чек-лист задач
    └── archive/
        └── <ГГГГ-ММ-ДД>-<слаг>/  — завершённые изменения
```

Слаг изменения — ASCII kebab-case, краткий и говорящий (например `add-dark-mode`, `avtozapolnenie-rekvizitov`).

## Порядок команд

1. `/исследовать <тема>` — изучить проблему и код, без изменений.
2. `/предложить <название>` — создать папку изменения с четырьмя артефактами.
3. `/реализовать <изменение>` — выполнить задачи из `tasks.md`.
4. `/проверить <изменение>` — сверить реализацию со спекой.
5. `/архивировать <изменение>` — перенести требования в `specs/`, папку — в `archive/`.

## Формат требований (`specs/`)

Плоский Markdown, без спецсинтаксиса. Требования пишутся сценариями:

```markdown
## ADDED Requirements

### Requirement: Контроль вместимости при проведении посещения
При проведении документа `ПосещениеАттракциона` система ДОЛЖНА проверять, что число
активных посещений аттракциона за текущий сеанс не превышает его вместимость.

#### Scenario: Посещение в пределах вместимости
- **WHEN** вместимость аттракциона 20, активных посещений 19, проводится новое посещение
- **THEN** документ проводится, движений добавляется на 1 посещение

#### Scenario: Превышение вместимости
- **WHEN** вместимость аттракциона 20, активных посещений 20, проводится новое посещение
- **THEN** проведение отменяется (`Отказ`), движений не формируется, выводится сообщение
  о превышении с указанием аттракциона

#### Scenario: Вместимость не задана
- **WHEN** у аттракциона вместимость не заполнена, проводится посещение
- **THEN** проверка вместимости пропускается, документ проводится
```

- `## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements` — дельта изменения.
- `### Requirement: <название>` — требование, формулируется в терминах ДОЛЖНО.
- `#### Scenario: <название>` — конкретный сценарий с **WHEN** / **THEN**.

## Дисциплина

- Не расширяй объём реализации за пределы `tasks.md`; появившиеся отклонения фиксируй в `design.md` и `tasks.md`.
- Спецификация — источник истины; черновик можно вести в режиме Планирования, но итог переносится в `openspec/`.
- Артефакты — plain Markdown, коммитятся в git вместе с кодом.
- Завершённое изменение не удаляется, а архивируется — история решений сохраняется.
