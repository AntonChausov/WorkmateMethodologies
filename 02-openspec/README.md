# 02. OpenSpec — живые спецификации и цикл изменения

**Источник:** OpenSpec. Это базовая версия; расширенная (EARS, граничные случаи, тесты по сценариям) — в `03-openspec-ears`. Ставится только одна из двух.

## Идея

Сначала спецификация, потом код. Каждое заметное изменение проходит цикл «исследование → предложение → ревью человеком → реализация → проверка → архив». Актуальные требования копятся в «живых» спецификациях `openspec/specs/` рядом с кодом в git.

Зачем в 1С: договориться о граничных случаях до того, как агент начнет менять метаданные (там ошибка дороже всего); ревьюить план (какие объекты, какие модули), а не большой дифф; держать агента в рамках чек-листа `tasks.md`; сохранить историю решений.

## Что внутри

| Файл | Назначение |
|---|---|
| `.workmate/commands/исследовать.md` | `/исследовать <тема>` — объекты, текущее поведение, 1–3 подхода; ничего не меняет |
| `.workmate/commands/предложить.md` | `/предложить <название>` — папка `openspec/changes/<слаг>/`: `proposal.md`, `specs/`, `design.md`, `tasks.md` |
| `.workmate/commands/реализовать.md` | `/реализовать <изменение>` — выполняет `tasks.md`, отмечает `[x]` |
| `.workmate/commands/проверить.md` | `/проверить <изменение>` — сверка требований и сценариев с кодом |
| `.workmate/commands/архивировать.md` | `/архивировать <изменение>` — требования в `openspec/specs/`, папка в `archive/` |
| `.workmate/skills/rabota-so-specifikaciyami/SKILL.md` | навык «Работа со спецификациями»: структура `openspec/`, формат требований WHEN/THEN, порядок команд |
| `openspec/README.md` | описание процесса — кладется в корень проекта EDT |

**Уровень установки:** проект (`openspec/` живет в проекте и коммитится вместе с кодом).

## Как пользоваться

1. `/исследовать <тема>` — агент только читает.
2. `/предложить <название>` — **отревьюйте и поправьте артефакты руками**: требования, сценарии, список объектов метаданных, задачи. Это главная точка контроля.
3. `/реализовать <слаг>`.
4. `/проверить <слаг>` — отчет агента не заменяет независимую проверку: маркеры EDT, прогон тестов YAxUnit, дифф.
5. `/архивировать <слаг>` — коммит.

Следующая задача по той же области начинается с чтения `openspec/specs/`.

## Что показал эксперимент

- Полный цикл и повторная задача по той же области на Напарнике работают (проверено пользователем, октябрь 2026).
- Механика (создать папку, заполнить четыре файла, отметить чекбоксы) — надежно; полнота сценариев, корректное слияние дельт при архиве и честная самопроверка требуют человека.

## Ограничения и известные доработки

- `/проверить` — самопроверка агента; без маркеров EDT и прогона тестов ее результат не подтвержден.
- `/архивировать` не описывает явно слияние `MODIFIED`/`REMOVED` с `openspec/specs/` — проверяйте результат.
- Нет отдельных конвенций описания метаданных в `design.md`.
- Пример слага в навыке (`add-dark-mode`) — не из 1С.
