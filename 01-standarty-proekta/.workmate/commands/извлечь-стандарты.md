Извлеки стандарты проекта по области. Аргумент: {{ARGUMENTS}}

Формат аргумента: `<область>` [, необязательно — объект метаданных или подсистема для сужения].
Область — строго одно из: `moduli`, `zaprosy`, `bsp`, `formy`. Если область не указана или указана иначе — остановись и переспроси.

ЖЁСТКИЕ ОГРАНИЧЕНИЯ
- Не изменяй исходники конфигурации и расширения (`.bsl`, `.mdo`, `.form` и пр.).
- Не трогай навык `.workmate/skills/standarty-proekta/` и `WORKMATE.md` — они обновляются только командой `/принять-стандарты`.
- Единственный результат этой команды — рабочие файлы в `.workmate/standards/`. Код не пиши.
- Запись файлов: если запись доступна (режим «Агент») — создавай и меняй файлы сразу, по шагам команды. Если работаешь в режиме «Планирование» (только чтение) — файлы не пиши: внеси в план отдельный пункт на каждый файл, который команда создала бы или изменила, с его содержанием; эти пункты проверяются при правке плана и выполняются при его исполнении. В режиме «Планирование» подзадачи (`explore`) возвращают выписку в формате файла сбора прямо в ответе; отметки `прочитан` и пути бери из этих ответов, а сам файл сбора включи в план отдельным пунктом.

1. ОПРЕДЕЛИ ОХВАТ (первым шагом, до любого анализа)
   - Составь список СОБСТВЕННЫХ объектов конфигурации — тех, что НЕ входят в подсистему `СтандартныеПодсистемы`. Состав подсистемы проверяй фактически (состав подсистемы через `1C_Find` / `GetObject_in_Project` или файл `Subsystems/СтандартныеПодсистемы`), НЕ угадывай по именам объектов.
   - Пройди ВСЕ типы объектов, а не только справочники и документы: справочники, документы, регистры накопления, регистры сведений, обработки, отчёты, общие модули, планы видов характеристик и прочие — что реально есть в конфигурации.
   - Для каждого собственного объекта найди модули (объектный, менеджера, формы, команд) и определи, есть ли в них тексты запросов (для `zaprosy` — поиск `ВЫБРАТЬ`, `Новый Запрос`, `МенеджерВременныхТаблиц` и т.п.).
   - Запиши в черновик раздел «Охват»: список «объект — модуль — есть ли запросы — отметка `прочитан`». На этом шаге — БЕЗ отметок: их проставит п. 2 по файлу сбора.
   - Расширения конфигурации (в том числе расширение с тестами YAxUnit) в охват НЕ входят: анализируется только основная конфигурация.

2. ОБРАБОТКА ПОДЗАДАЧАМИ И ФАЙЛ СБОРА (экономия контекста)
   - Основной диалог модули ЦЕЛИКОМ не читает. Его работа: «Охват» (п. 1) → разбивка на группы → запуск подзадач → свод файла сбора → поиски отклонений (п. 5), проверка порога (п. 6), сверка с ИТС (п. 7) → черновик и реестр (п. 8).
   - Раздели модули «Охвата» на группы по 5–8 объектов.
   - Каждую группу обрабатывай в ОТДЕЛЬНОЙ подзадаче (`Task`), последовательно, по одной. Подзадачи НЕ запускать параллельно.
   - Тип подзадачи — с правом записи файлов (не `explore`: он только читает и не сможет дописать файл сбора).
   - Подзадача по модулям своей группы: читает модули, читает по ним маркеры EDT (`GetMarkers`), ищет паттерны, нарушения и ошибочный код.
   - Подзадача дописывает в `.workmate/standards/сбор-<область>.md` по каждому модулю: отметку `прочитан`; наличие маркеров уровня «ошибка»; найденные паттерны с путями:строками; нарушения; ошибочный код; маркеры области с идентификатором проверки.
   - Отметку `прочитан` в разделе «Охват» черновика ставь ПО ФАЙЛУ СБОРА, а не по собственному `Read` основного диалога.
   - Модуль «Охвата» без отметки `прочитан` в файле сбора — пробел в анализе; перечисли такие модули в резюме.
   - Файл сбора НЕ удаляй — он нужен человеку для проверки.

3. ЧТО СМОТРЕТЬ ПО ОБЛАСТЯМ
   - `moduli` — объектные модули и модули менеджеров справочников/документов/регистров, общие модули, модули форм, модули команд. Аспекты: именование (объекты, реквизиты, переменные, процедуры), структура модуля и областей (`#Область`), директивы компиляции и клиент-серверное взаимодействие, обработка ошибок (`Попытка`/`Исключение`) и транзакции (`НачатьТранзакцию`/`ЗафиксироватьТранзакцию`).
   - `zaprosy` — тексты запросов внутри модулей: параметры vs конкатенация, оформление текста, соединения, временные таблицы, менеджер временных таблиц.
   - `bsp` — какие механизмы БСП приняты в проекте вместо собственных реализаций: повторяющиеся вызовы общих модулей БСП и повторяющиеся самописные аналоги тех же задач.
   - `formy` — модули форм: набор и порядок обработчиков, повторно используемые фрагменты, структура командного интерфейса формы.

4. ИНСТРУМЕНТЫ (используй все три канала, не полагайся на память)
   - Поиск по метаданным: `1C_Find` (scopes: catalogs, documents, information_registers, accumulation_registers, common_modules, forms, ...) — чтобы выбрать объекты и модули охвата.
   - Поиск по файлам: `SearchText` по `*.bsl`/`*.mdo` (например `#Область`, `Новый Запрос`, `НачатьТранзакцию`, `Попытка`, `СтрШаблон`).
   - Ограничивай текстовый поиск папкой `src` основной конфигурации (путь проекта + `src`); не ищи по всему воркспейсу.
   - Если поиск вернул «совпадений нет» — НЕ повторяй тот же запрос: измени маску/запрос либо прочитай модуль напрямую (`Read`): целиком — в подзадаче, в основном диалоге — только фрагмент вокруг нужной строки. Холостые повторы запрещены.
   - Семантический поиск и чтение: `FindSimilar_in_Project` / `FindRelated_in_Project` — похожие реализации и методы; `Glob` → `Read` — чтобы прочитать найденные модули целиком и увидеть контекст (целиком — только в подзадачах, см. п. 2); `GetObject_in_Project` — состав объекта.
   - Проверка общих норм: `mcp__knowledge-hub__Search_ITS` (стандарты разработки 1С и БСП) — чтобы НЕ записывать общее и корректно пометить отступления.
   - Маркеры EDT: `GetMarkers` выполняется в подзадачах (п. 2); основной диалог берёт маркеры из файла сбора.

5. СОБЕРИ ДОКАЗАТЕЛЬСТВА ПО КАЖДОМУ КАНДИДАТУ
   - Формулировка правила (что именно делать).
   - Число мест «следуют» — с путями `файл:строка`; число мест «отклоняются» — с путями.
   - 2–3 пути-примера со строками (для «следуют» и, если есть, для «отклоняются»).
   - Каждый путь указывай ТОЛЬКО если модуль фактически прочитан (основным диалогом или подзадачей) и зафиксирован в файле сбора. Нет записи в сборе — путь не указывай: лучше меньше путей, чем выдуманные.
   - ИСКЛЮЧИ модули с ошибками EDT: если по модулю в файле сбора отмечен маркер уровня «ошибка», его пути не включай ни в «следуют», ни в «отклоняются». Находки по такому модулю идут только в реестр отклонений (п. 7).
   - Отклонения ищи ЯВНО, а не «замечай по ходу чтения»: для каждого кандидата сформулируй поисковый запрос, находящий нарушения (например, `Новый Запрос` внутри цикла; запрос без параметров), выполни его по всему охвату (в границах `src`, см. п. 4) и добавь в правило поле `**Поиск отклонений:** <запрос> → <число найденных>`. Из найденного исключи модули с маркером «ошибка» (см. выше); указывай число после исключения — это и есть M.
   - Ищи реальную альтернативу паттерну — то, что в проекте пишут ВМЕСТО правила (например, для правила «сообщения через `СообщениеПользователю`» — вызовы `ОбщегоНазначения.СообщитьПользователю`), а не вариации написания самого правила.

6. ПРОВЕРКА ПОРОГА (механически, без «на глаз»)
   - «утверждено» НЕ проставляй — статус ставит человек, правя черновик.
   - Для каждого кандидата посчитай: N — мест «следуют», K — число разных объектов метаданных, M — отклонений: число из поля «Поиск отклонений» (п. 5), оно же — M в поле «Доказательства».
   - Добавь в правило поле `**Проверка порога:** мест N, объектов K, отклонений M → <статус>`.
   - Статус ставь строго по формуле: N ≥ 3 И K ≥ 2 И M < N → `кандидат`; иначе если N < 3 или K < 2 → `наблюдение`; иначе → `разнобой`. Решение по не-кандидатам принимает человек.

7. ОТКЛОНЕНИЯ И СВЕРКА С ИТС
   - Объективно ошибочный код (например: транзакция без обработки исключения и отката, деление без проверки делителя, выполнение кода из внешних данных) идёт в реестр отклонений, ДАЖЕ если повторяется. Повторяемая ошибка в стандарты не попадает.
   - Перенеси в реестр маркеры области из файла сбора (п. 2) — те, что относятся к области (для `zaprosy` — например, запрос в цикле), с идентификатором проверки (код/номер маркера).
   - По каждому правилу выполни поиск в ИТС (`mcp__knowledge-hub__Search_ITS`) по сути правила и добавь в правило поле `**ИТС:** <найдено ли аналогичное требование; название документа>`:
     • Если общий стандарт требует или рекомендует ТО ЖЕ — правило в черновик НЕ включай; добавь одну строку в раздел «Совпадает с общими стандартами (не включено)».
     • Если практика проекта расходится с требованием или рекомендацией общего стандарта (в том числе БСП) — включай правило только с основанием «отступление от общих стандартов», никогда «специфика проекта».
   - Нарушение общего стандарта в коде проекта — пункт реестра отклонений, а не строка «Совпадает с общими стандартами»: этот раздел — только для правил, которым проект следует.

8. ВЫХОДНЫЕ ФАЙЛЫ
   - `.workmate/standards/сбор-<область>.md` — файл сбора подзадач (п. 2). НЕ удалять — нужен человеку для проверки.
   - `.workmate/standards/черновик-<область>.md` — разделы: «Охват» (из п. 1 + отметки `прочитан` из п. 2), «Правила» (формат из п. 9), «Совпадает с общими стандартами (не включено)» (из п. 7). Создай папку при необходимости. Существующий черновик по этой области дополняй, не затирая чужие статусы. Повторный запуск по той же области (например, с другим сужением): правило с тем же именем не дублируй — объедини доказательства и пересчитай порог (п. 6) по всем местам; «Охват» дополняй новыми объектами; в файле сбора начинай отдельный раздел текущего запуска (дата и охват).
   - `.workmate/standards/отклонения.md` — дополнение: раздел на область, пункты вида «что не так — пути:строки — почему ошибка — идентификатор проверки EDT».
   - В конце ответа — короткое резюме: сколько кандидатов, наблюдений, разнобоя и отклонений; пробелы анализа (модули «Охвата» без отметки `прочитан` в файле сбора); напомни, что правила попадут в навык только через `/принять-стандарты`.

10. ЧЕГО НЕ ДЕЛАТЬ
- Не читай модули целиком в основном диалоге — это делают только подзадачи (п. 2); основной диалог сводит файл сбора.
- Не удаляй файл сбора `.workmate/standards/сбор-<область>.md`.
- Не запускай подзадачи параллельно — только последовательно.
- Не повторяй поисковый запрос, вернувший «совпадений нет», — меняй запрос/маску или читай модуль напрямую (целиком — только в подзадаче).
- Не записывай общие стандарты разработки 1С и БСП, которые ты и так знаешь, — только специфику проекта и отступления от общего (с пометкой «отступление»). Совпадение с общим стандартом — строкой в раздел «Совпадает с общими стандартами (не включено)».
- Не включай в доказательства пути из модулей с ошибками EDT (маркер уровня «ошибка») — только в реестр отклонений.
- Не оставляй модули «Охвата» без отметки `прочитан` молча — перечисляй их как пробелы в резюме.
- Не выводи правило из отсутствия конструкции: «в коде нет внутренних соединений» — не правило «только ЛЕВОЕ СОЕДИНЕНИЕ». Правило — только то, что проект делает в N местах.
- Не переноси правила в навык и не меняй `WORKMATE.md`.
- Не формулируй правило как пожелание («следуй лучшим практикам») — только конкретный проверяемый рецепт с примерами из кода.
