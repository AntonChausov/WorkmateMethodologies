# 03. OpenSpec + требования EARS и сценарии → тесты

**Источники:** OpenSpec (Scenario), Kiro (EARS). Расширенная версия `02-openspec`; ставится только одна из двух.

## Идея

- **EARS** — пять шаблонов формулировки требования: всегда / КОГДА (событие) / ПОКА (состояние) / ЕСЛИ…ТО (нежелательное поведение) / ГДЕ (опция). Одно требование — одна проверяемая реакция.
- **Сценарии WHEN–THEN с конкретными значениями** («лимит 5, продано 4, проводится 2 → отказ»), при зависимости от даты — опорная дата.
- **Чек-лист граничных случаев 1С** (повторное проведение, отмена, границы суток, пустые значения, срезы регистров, конкурентность): по каждому пункту спека обязана сказать «покрыт сценарием» / «неприменим: почему» / «ручная проверка: почему».
- **Сценарий → тест YAxUnit**: данные сценария → тестовые данные, WHEN → действие, THEN → проверки. Тест пишется по спеке, а не подгоняется под готовый код.

## Что внутри

Все файлы `02-openspec` (тексты `предложить`, `проверить`, `архивировать` и навыка — расширенные) плюс:

| Файл | Назначение |
|---|---|
| `.workmate/commands/сгенерировать-тесты.md` | `/сгенерировать-тесты <изменение>` — тесты YAxUnit по сценариям + таблица покрытия |
| `.workmate/skills/rabota-so-specifikaciyami/references/ears-i-scenarii.md` | шаблоны EARS, правила качества требований и сценариев, чек-лист граничных случаев 1С |

Изменения в остальных командах: `/предложить` — требования по EARS и раздел «Граничные случаи»; `/проверить` — таблица покрытия «сценарий → тест»; `/архивировать` — не архивирует, если у сценария нет теста и нет обоснованного пропуска.

**Уровень установки:** проект.

## Как пользоваться

`/исследовать` → `/предложить` → **ревью спеки человеком** → `/реализовать` → `/сгенерировать-тесты` → **прогон тестов человеком** (Напарник тесты не запускает) → `/проверить` → `/архивировать`.

## Что показал эксперимент

- Методика **не увеличила число найденных граничных случаев**: и без нее агент находит около ¾ эталона (≈12 из 16), с ней — столько же; все варианты пропустили одни и те же случаи.
- Польза в другом: тесты пишутся по спеке и проверяют заказ, а не реализацию; раздел «Граничные случаи» делает ревью прозрачным — видно, что агент счел неприменимым и почему.
- Тесты из `/сгенерировать-тесты` после независимого прогона: 9 из 12 сразу, 12 из 12 после разбора падений и синхронной правки спеки и тестов.
- Цена — контекст: до 60% на генерации тестов.

## Ограничения и известные доработки

- Тесты на отказ проведения: не обращайтесь к базе после исключения внутри `ВТранзакции()` — «В данной транзакции уже происходили ошибки». Агент регулярно попадает в эту ловушку.
- Проверяйте различающую силу тестов: упал бы тест, если сломать проверяемую ветку кода?
- Тесты сейчас может писать и `/реализовать` (через `tasks.md`), и `/сгенерировать-тесты` — договоритесь об одном месте.
- Изменение ожиданий теста — только вместе с THEN в спеке и записью в `design.md`.
